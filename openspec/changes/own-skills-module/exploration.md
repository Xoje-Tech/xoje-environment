## Exploration: First-party skills module

### Current State
Xoje is a Go 1.22+ CLI/TUI (`cmd/xoje`) with thin command dispatch in `main.go`, parsing in `internal/cli`, Bubble Tea interaction in `internal/tui`, tool installation/update in `internal/install`, JSON state in `internal/config`, executable verification in `internal/verify`, and composable health checks in `internal/doctor`. The current command surface is `version`, `doctor`/`diagnose`, `install <tool>`, `update [tool]`, `update-all`, and `tui`; an empty invocation enters the TUI. The TUI currently exposes doctor, install-tools, update-fleet, and exit actions.

`internal/install` has a hard-coded `Registry` for `gentle-ai` and `dev-tracker`, supports Go-module and GitHub-release installers, writes binaries to `~/.local/bin`, records installed tool names in `~/.config/xoje/config.json`, and on gentle-ai update delegates ecosystem upgrade and skill synchronization to `gentle-ai upgrade` then `gentle-ai sync`. `internal/doctor` already wraps native gentle-ai health reporting alongside host/tool checks. This establishes a thin-wrapper/cascade boundary: Xoje should orchestrate first-party skill ownership and invoke supported native ecosystem operations, not reimplement gentle-ai internals.

The repository has no project-level `skills/` directory, no agent adapter directories, and no `AGENTS.md`; `.atl/skill-registry.md` was generated by `sdd-init` and indexes user/global skills. It explicitly records project skill directories as absent, says it is an index rather than a summary, and requires re-scanning when project skills are added. Therefore it must remain a discovery/SDD index, not the canonical source of first-party skills. Hermes owns `~/.hermes/skills/`; Xoje must not overwrite, vendor, or silently mutate that global boundary.

OpenSpec is configured as `spec-driven`, with English artifacts, Given/When/Then scenarios, RFC 2119 terms, strict TDD, `go test ./...`, `go build ./...`, and domain-decoupling guidance. Existing and archived changes use one proposal/design/tasks lifecycle and domain-separated specs. The current test suite covers command parsing, config persistence, installer behavior, doctor checks/aggregation, TUI navigation, executable verification, and `cmd/xoje` dispatch. `go test ./...` currently passes across all packages (cached); no production files were changed during this exploration.

Reference findings from CodelyTV/agent-harness are useful but not authoritative: a canonical common skills source projected into per-agent locations, declarative catalog/manifest metadata, `SKILL.md` frontmatter, plugin/hooks, and GitHub/RPI variants. Its npm preparation is invalid and its `AGENTS.md` is stale, so those mechanics and unsupported-agent claims must not be copied without local validation.

### Affected Areas
- `cmd/xoje/main.go` — add future command wiring only after the domain API is defined; preserve current dispatch and TUI action model.
- `internal/cli/cli.go` — extend parsing for explicit skill lifecycle commands (likely list/verify/sync/install or equivalent), with aliases documented by OpenSpec.
- `internal/tui/tui.go` — expose skill status/sync onboarding only through commands supported by the domain layer; keep Bubble Tea as an adapter, not the owner of filesystem logic.
- `internal/install/install.go` — integrate skill synchronization with explicit, idempotent orchestration; do not conflate binary `Registry` entries with skill catalog records.
- `internal/config/config.go` — add versioned, backward-compatible skill-module state only if needed; preserve existing JSON location and load-or-create behavior.
- `internal/doctor/checks.go` — add read-only skill-manifest/target integrity checks and actionable remediation, while retaining gentle-ai doctor delegation.
- `internal/verify/verify.go` — reuse executable/path verification; skill verification should be a separate domain concern rather than a generic `LookPath` expansion.
- `openspec/specs/` — likely add a dedicated first-party skills capability and modify CLI, diagnosis, and configuration capabilities through delta specs.
- `.atl/skill-registry.md` — regenerate/update as an index after implementation; never use it as the source of skill content.
- New future module boundaries: canonical `skills/` content, manifest metadata, generated registry output, and explicit agent adapters/sync targets. Hooks/plugins are non-goals unless a target agent has a documented supported and secure extension contract.

### Approaches
1. **Project-canonical skills with explicit adapters and sync** — store authored skills under repository `skills/<name>/SKILL.md` plus validated frontmatter and a manifest; generate a deterministic registry; implement an allowlisted adapter per supported agent and an idempotent sync command with dry-run, atomic writes, path validation, and safe fallback.
   - Pros: clear ownership; reproducible builds; auditable generated state; supports multiple agents without symlink assumptions; preserves Hermes global-skill ownership; testable in Go.
   - Cons: requires manifest/schema validation and adapter capability matrix; migration needs careful conflict policy.
   - Effort: Medium/High

2. **Common source projected by symlinks** — mirror the Codely pattern by linking each agent’s skill directory to a common repository source.
   - Pros: low duplication and simple updates.
   - Cons: brittle across platforms and agent layouts; unsafe with existing directories; unclear ownership and deletion semantics; does not fit Hermes global-skill boundary; unsupported agents become accidental claims.
   - Effort: Medium

3. **Delegate all skills to Hermes/gentle-ai** — keep no project-owned skill content and invoke ecosystem sync only.
   - Pros: minimal Xoje code and no duplicate storage.
   - Cons: fails the first-party module goal; cannot provide repository-versioned skills, generated registries, onboarding, or controlled adapters; couples behavior to external availability.
   - Effort: Low, but insufficient

### Recommendation
Choose Approach 1. Define a Go domain/application service for manifest loading, validation, registry generation, target discovery, and sync; keep filesystem and process operations behind ports so unit tests use temporary directories and fakes. Make `skills/` the canonical authored source, with stable skill IDs, schema/version metadata, ownership, supported-agent declarations, and checksums or generated registry fingerprints. Treat generated registries as derived artifacts and fail verification on drift rather than editing them at runtime.

Implement only explicit, capability-declared adapters (initially the agents that can be verified locally). Sync MUST be idempotent, path-confined, atomic, and non-destructive by default; it SHOULD support dry-run and a safe fallback when a target is absent or unsupported. Never write into `~/.hermes/skills/` as part of project sync; instead expose Hermes as an external/global source boundary and document when native `gentle-ai sync` is the correct operation. Hooks/plugins should be represented only as optional manifest capabilities backed by a documented allowlist, signature/trust policy, and no shell execution by default. Do not claim Codely/GitHub/RPI adapters until each target contract exists and is tested.

Onboarding should be an explicit command/flow that detects existing targets, previews changes, asks for or records a migration policy, and writes only declared managed paths. Migration should preserve unmanaged user files, detect collisions, require explicit overwrite/backup decisions, and be resumable. RPI/OpenSpec integration should be documentation and generated-registry metadata first: skills can describe RPI workflows, but the module must not embed an RPI runner or assume a particular agent protocol. Define proposal/spec/design/tasks deltas before implementation.

### Risks
- Ambiguous ownership between repository skills, generated targets, Hermes global skills, and gentle-ai native sync can cause destructive overwrites or drift.
- Agent directories and plugin/hook contracts vary; unsupported targets may be silently misconfigured unless capability detection and an allowlist are mandatory.
- Symlink or path traversal behavior can escape the project root; use canonicalized paths, confinement checks, atomic staging, and explicit permissions.
- Generated registry drift and hand-edited derived files can make onboarding non-reproducible; verification must compare generated output deterministically.
- Existing users may have unmanaged skills in target directories; migration needs collision, backup, rollback, and idempotency semantics before coding.
- Network/native ecosystem operations are not required for core project sync; accidental coupling to `gentle-ai upgrade/sync` could make offline verification flaky.
- The current OpenSpec config notes Go availability as a prerequisite, while the live repository currently passes `go test ./...`; verify environment assumptions in later phases rather than encoding the stale note into behavior.
- Codely reference artifacts include invalid npm preparation and stale agent instructions; external patterns require local validation and must not override repository conventions.

### Ready for Proposal
Yes. The exploration supports a proposal for a project-owned, Go-only skills module with canonical `skills/`, manifest and generated-registry contracts, explicit supported-agent adapters, secure/idempotent synchronization, Hermes/gentle-ai boundary rules, onboarding/migration, and OpenSpec/RPI integration. The proposal should first decide the initial supported-agent matrix, manifest schema/version, generated-file location, collision/rollback policy, and whether the first delivery is verify/list/sync only or includes install/onboarding in the same change.
